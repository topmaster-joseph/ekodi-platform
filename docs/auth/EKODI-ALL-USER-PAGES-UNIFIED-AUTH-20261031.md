# EKODI 사용자 전체 통합 인증 강제 계약 (2026-10-31)

## 범위 및 강제 규칙

- `EKODI_SERVICE_MANIFEST.services`의 사용자 서비스 **37개 전부**에 하나의 EKODI Person/ekodi_id를 사용한다. 기존 Shell 연동 선언 33개, 계획 단계 4개. 등록 수와 운영 로그인 E2E 성공 수는 별도 지표로 관리한다.
- 모든 사용자 공개/워크스페이스 화면은 `https://ekodi.kr/auth/`에 접근할 수 있는 공통 로그인 UI를 제공한다. 별도의 인증 도메인이나 서비스별 회원가입을 새로 만들지 않는다.
- **로그인 강제와 통합 인증의 강제 적용은 다르다.** 공개 페이지는 계속 비회원 열람 가능하다. 쓰기·회원 혜택·결제·관리자·조직 자료는 실제 기능 API에서 EKODI Person, Workspace, 역할, 플랜을 독립 검증한다.
- 개별 사이트의 브랜드/네비게이션/독립 배포 경로는 유지할 수 있으나 사용자 회원 신원 저장소와 중앙 로그인의 대체가 될 수 없다. 독립 배포 필요성은 격리·법인 책임·장애 범위·배포 책임으로만 판단한다.
- 반환 주소는 사용자 로그인 직전의 `origin + pathname + search`. 중앙 인증 허용 목록에 등록된 안전한 사이트/경로만 복귀시킨다. `/my`로 자동 우회 금지.
- 공통 헤더에는 이메일/UUID/token을 출력하지 않는다. `people.display_name`을 우선으로, 실패 시 사용자 메타데이터의 display_name/name만 **화면 라벨로** 참고한다. 화면 최대 12자 + 줄임표, 저장된 이름과 내부 고유 ID는 변경하지 않는다. 메타데이터는 절대로 권한 근거로 사용하지 않는다.
- 로그아웃은 서비스 세션과 중앙 세션 간 단일 로그아웃 계약이 검증되기 전까지 공통 이름 라벨에서 임의 구현하지 않는다. 기존 서비스별 유효한 로그아웃 동작은 유지한다.
- 새로운 회원용 공급자 활성화는 별도 제공자 서버 키/콜백/회귀·승인을 확인한 뒤에만. 공급자 목록의 `enabled=true`만으로 운영 성공을 선언하지 않는다.

## 복수 계정이 '동일한 사람'임을 증명하는 절차

1. 사용자가 기존 EKODI ID로 로그인하고 서버가 실제 세션의 `auth.uid()`와 연결된 `person_id`를 확인한다.
2. **로그인 수단 추가**를 사용자가 직접 시작하고 단기 nonce, state, issuer, audience, provider subject, 만료 및 재사용 방지를 적용한다.
3. 두 번째 Google/카카오/네이버/이메일 계정을 **공급자 공식 인증 화면에서 별도로 재인증**한다. 동일한 이메일, 이름, 전화번호, 브라우저나 IP는 동일인 확인 근거가 아니다.
4. `login_identities`의 `provider + provider_subject`가 이미 다른 Person에 귀속되는지 서버 트랜잭션으로 확인한다. 다른 Person에 속한다면 자동 링크/병합 금지, HTTP 409 검토 대기로 처리한다.
5. 추가 계정이 미연결 상태이며 소유권이 입증되면 검증된 공급자 신원을 기존 Person에 등록한다. 유료 멤버십, 관리자 권한, 자금/포인트, 조직 데이터는 독립된 서버 원장으로 유지한다.
6. 연결 이후 각 공급자로 로그인할 때 `current_ekodi_identity()`가 동일 `person_id`와 `ekodi_id`를 반환하는지 검사한다. 한쪽 로그아웃/탈퇴/복구/연결 해제 시 다른 사람 계정으로 승격되지 않도록 회귀 테스트한다.
7. Supabase Auth에는 **검증된 동일 이메일의 OAuth 자동 신원 연결 기능**이 있으므로, GoTrue `auth.users` 동일성만을 EKODI의 명시적 연결 승인으로 해석하면 안 된다. Person 수준의 연결 의도·소유권과 충돌 검사를 서버에서 별도로 요구한다.

## 운영 출시 가드

1. Node 검사: `node --check shell/unified-user-auth.js`; `node --test test/unified-user-auth.test.mjs`; 전체 `npm test`, 헌법/도메인/인증·오케스트레이터/병행 변경 가드.
2. Staging: 서비스 37개 레지스트리 체크, 실제 제공되는 모든 사용자 경로의 공통 로그인 버튼, 웹·모바일 헤더 폭, 12자 이름 표시, 한글 이름, 로그아웃 상태, 하위 페이지·쿼리 복귀.
3. 기존 Google 경로와 회원/작업/관리자/구독·외부 개인 도메인 로그인 후 복귀를 훼손하지 않는다. 관리자 D1 및 결제/계정병합 PR과 독립적 출시 범위로 유지한다.
4. EKODI Orchestrator 보호 PR, 정확한 커밋 SHA CI 및 릴리스 영수증, 스테이징과 운영 Worker 실화면 및 서버 계정검증 401/403/200 증명 후에만 운영 완료 보고한다.
5. 모든 서비스의 개별 배포 자동화를 무조건 통합하지는 않는다. 공통 인증 모듈의 배포는 Shell 배포가 담당하며, 각 독립 Worker는 권한 API와 handoff를 개별 검증한다.
