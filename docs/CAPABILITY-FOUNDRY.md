# EKODI Capability Foundry

## Principle

EKODI accumulates reusable capabilities before creating a new user-facing service.

`Need → internal family → module candidate → sandbox → verified module → sample composition → repeated evidence → user request/measured need → service composition`

A capability or module may exist internally for a long time without becoming a public service.

## Internal families

Foundry families are implementation-oriented and deliberately separate from public service brands or workspace domains: knowledge, document, language, media, data, workflow, communication, integration, identity/access, realtime, commerce, and safety/verification.

## Sample Service

The Capability Sample Service is available only inside the administrator Capability Center. It uses fixed synthetic inputs, does not call external networks, does not write production data, does not persist inputs, and cannot create a user service.

Initial recipes:
- Official update brief
- Multilingual event kit
- Small-business campaign kit

A successful sample means only that the module/capability composition is structurally reusable. It is not product-market validation.

## Service creation gate

A user-facing service can be considered only after:
1. existing capabilities and shared runtime have been evaluated first;
2. the composition has at least three verified sample runs;
3. a user request or measured recurring need exists;
4. human review approves packaging;
5. a dedicated deployment boundary, if proposed, independently satisfies the constitutional boundary-creation gate.

This keeps EKODI capability-rich without turning every useful idea into another site or service.
