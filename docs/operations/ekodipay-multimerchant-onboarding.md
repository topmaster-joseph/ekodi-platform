# EKODI Pay: 사업자별 PG MID·정산계좌 독립 운영 절차 (설계 및 구축 현황)

> 이 문서와 함께 도입되는 코드는 **사업자 검증 계약·정산 대사 기능의 비금융 구현**입니다. 실제 돈을 청구하거나 송금하지 않습니다. 기존 운영 `ekodi.kr/ekodipay/`는 계속 실결제 비활성화입니다. 모든 변경은 공식 EKODI 오케스트레이터·보호된 병합 및 최종 재무 승인으로 처리합니다.

## 1. 계정 구조: 사업자마다 실제 계약 주체가 명확해야 함

| 주체 | 역할 | 분리 의무 |
|---|---|---|
| EKODI Pay | 공통 UI, 결제 모듈, 감시·감사 | 직접 정산금 수취나 재송금 **하지 않음** |
| 사업자 A | PG 계약·상점 MID·정산계좌·세무·고객응대 | 독립 `merchantId` / `legalEntityRef` |
| 사업자 B | 별도 PG 계약·상점 MID·정산계좌 | A의 API 키, 원장 및 주문 조회 권한 공유 금지 |
| 사업자별 승인된 주문 발급기 | 서버에서 세금·할인·최종 원화 금액과 만료시각 확정 | 판매자, 발급 서비스, 승인 참조값을 **서버 인증 후** 불변 저장 |
| EKODI 최고관리자 | 전체 **비밀 없는** 상태 및 감사 조회 | 이체 권한 없음, 무단 MID 변경 금지 |

- EKODI Biz, EKODI Mall, EKODI Education 등은 *서비스명*이고, 실제 계약상 **누가 판매자인지** 별도 확인한 뒤 `merchantId`와 `legalEntityRef`에 연결합니다.
- 한 법인이 여러 사이트를 운영할 경우 반드시 PG 계약 단위와 정산계좌의 관계에 맞춰 MID를 등록합니다. MID가 서비스별로 추가 발급되는 구조는 PG가 제공하는 결제서비스/MID 계약을 따릅니다.
- 결제대금을 EKODI가 모아서 사업자에게 지급하는 지급대행형 운영은 **별도 금융·법률 및 PG 계약 검토** 전에는 금지합니다.

## 2. 사업자별 외부 설정: 신청부터 라이브까지

1. **사업자 확정** — 실제 판매자의 법적 명칭, 사업자등록증/등록번호, 업종·재화/서비스, 통신판매업 신고 해당 여부, 사업장 주소, 고객센터, 전자상거래 약관, 개인정보처리방침, 청약철회·환불 규칙을 확인합니다. 비공개 문서 원본은 제한된 보관소에만 두고 외부 공개 PR/채팅에는 올리지 않습니다.
2. **토스페이먼츠 가맹점별 신청·심사** — [PG 전자결제 신청·개발자센터](https://developers.tosspayments.com/)에서 각 법적 판매자 계약을 진행합니다. 카드사·간편결제·계좌이체 제공 범위, 정산 주기와 수수료, 취소/환불 조건을 계약서로 확인합니다. 토스페이먼츠는 결제서비스별 MID를 발급할 수 있으므로 MID가 정확히 어느 사업자/서비스의 것인지 확인합니다.
3. **정산계좌 확인** — PG 관리자에서 그 사업자의 정산계좌 등록·계좌명의/사업자 대조·변경 승인 기록을 확인합니다. EKODI에는 `bankCode`, 마스킹 4자리, HMAC-SHA256 지문, 접근제한된 증명자료 참조와 검증자/날짜만 남기고 전체 계좌번호/예금주를 공개 DB·PR·코드/로그에 저장하지 않습니다. 계좌 지문은 **비공개 HMAC 키**로만 생성해야 하며 일반 SHA256만으로는 충분하지 않습니다.
4. **PG MID 및 테스트/운영 키** — 토스페이먼츠 관리자에서 계약 승인된 MID를 확인하고 같은 상점의 SDK v2 클라이언트키 `test_gck_`·`live_gck_`, 서버 시크릿키 `test_gsk_`·`live_gsk_`를 별도로 매칭합니다. 각 MID의 API 비밀키는 Cloudflare encrypted Worker secret(또는 이에 준하는 사업자별 접근 제한 비밀 관리자)에 등록합니다. **채팅·GitHub·사이트 등록 폼에 시크릿키를 입력하지 않습니다.**
5. **EKODI 비밀 바인딩** — 사업자마다 키 참조만 비공개 등록합니다. 예: `PAY_MERCHANT_A_TEST_CLIENT`, `PAY_MERCHANT_A_TEST_SECRET`, `PAY_MERCHANT_A_LIVE_CLIENT`, `PAY_MERCHANT_A_LIVE_SECRET` (가상 이름). 정확한 MID나 키는 코드 저장소에 넣지 않습니다. 같은 비밀 바인딩 또는 동일 `provider+mode+MID`를 두 사업자가 공유하도록 등록하면 거부합니다.
6. **승인 주문 발급기 연결** — 각 사이트의 백엔드에서 이미 승인된 거래만 EKODI Pay에 제출합니다. 구매자 입력 `merchantId`, `amount`, `approved`, `orderId`는 믿지 않습니다. 서버 간 인증, 불변 주문 ID·원화 금액·판매자·발급자·승인 참조·만료 시각, 중복요청 방지가 필수입니다. `ekodibiz` 단일 판매자 PG 코어 PR #4877은 아직 별도 구현/검증 중이며 다중 사업자 결제 연결까지 완성된 것이 아닙니다.
7. **웹훅·환불 관리** — PG 설정 화면에서 MID별 통보 경로를 지정합니다. 단, **현재 웹훅 구현이 차단(503)** 된 범위에는 URL을 등록하지 않습니다. 구현 뒤 HTTPS+서명·전송 ID 중복 방지, 별도 해당 MID API 재조회, 금액·주문·상태 일치, 실패 시 격리·재시도 확인 후 등록합니다. 환불은 승인자 분리, 멱등성, PG 조회와 회계 반영이 완료될 때만 해당 사업자 권한으로 허용합니다.
8. **정산 대사** — 각 MID의 비밀키로 `GET /v1/settlements?startDate=...&endDate=...`를 서버에서 조회합니다. 최대 페이지를 따라 모두 읽었다는 증거가 없으면 '대사 통과' 처리하지 않습니다. `mId`, `orderId`, `paymentKey`, `transactionKey`, `currency`, `amount`, `payOutAmount`를 독립 원장과 건별 비교합니다. 수수료 항목 `fees[]` 및 공급가액/부가세, 지급 예정일은 재무 담당자가 확인하고, **실제 계좌 입금은 해당 계좌의 인증된 거래내역으로 별도 검증**합니다.
9. **최종 라이브 허용** — 사업자별 정산/고객보호/PG 심사·소액 테스트/취소 검증, EKODI 오케스트레이터 릴리스, 별도 재무 책임자 승인 후 해당 사업자만 활성화합니다. 한 사업자 활성화가 다른 사업자를 자동 활성화하지 않도록 합니다.

## 3. EKODI 화면 설계

공통 주소는 계속 `https://ekodi.kr/ekodipay/`입니다. 최고관리자 내의 '결제 > 사업자 관리'에서 다음 데이터를 관리하는 흐름을 목표로 합니다.

- **사업자 현황**: 이름/내부 식별자, 이용 서비스, 사업자 승인 상태, PG 계약 확인, 결제 가능 여부.
- **MID·키 연결**: PG사, MID 마스킹 여부, 테스트/라이브 키 *등록 여부만*, 비밀 바인딩 참조, 폐기/회전 기록.
- **정산계좌**: 은행명/끝 4자리, 명의검증 증명서 참조, 확인일, 변경 이중승인(전체 계좌번호 출력 금지).
- **주문 발급기**: 담당 사이트, 서버 인증 상태, 승인/취소 권한, 원장 식별자.
- **정산 검증**: 사업자/MID/일자별 결제액·수수료·지급예정액·입금확인액 및 불일치 알림.
- **감사 로그**: 누가 언제 계약·계좌·키 참조·권한을 바꿨는지 변경 전후 메타데이터(비밀값 제외), 실패·재시도 기록.

일반 사용자는 자기 주문 결제만 확인합니다. 사업자 운영자는 **자기 사업자** 거래와 정산만, EKODI 최고관리자는 상태·감사만 조회하도록 서버에서 인증/인가를 강제해야 합니다.

## 4. 이번 PR에서 실제 구현한 것

- `ekodipay-merchant-contract.js`: 사업자별 MID 충돌 차단, 키 참조 격리, 서비스·승인 주문 발급자 매핑, 별도 증빙·재무 게이트, 공급사 `mId`/주문 ID 대조용 계약.
- `ekodipay-settlement-reconciliation.js`: 사업자/MID별 안전한 정산 조회 URL 생성, 완전한 PG 데이터와 내부 원장 건별 대조, 불일치 및 중복 격리, PG 정산 확인과 은행 입금 확인 **분리**. 순수 함수이며 PG 호출/계좌이체 수행하지 않음.
- `services/ekodipay/migrations/0001-private-multi-merchant.sql`: 비공개 D1 적용 예정 스키마. 자동 마이그레이션 **하지 않음**, 관리자 인증·데이터 암호화 및 전환 절차 확인 후 공식 보호 배포에서 실행.
- `test/ekodipay-multimerchant-contract.test.mjs`: 상점 간 키/MID 중복, 위조 주문, 독립 MID, 금액/지급액 오류, 미완료 페이지·은행 미입금 상황을 검증.

### 2026-10-17 추가: 주문 발급 HMAC 검증과 재사용 차단

- `ekodipay-order-attestation.js`: 발급기 주문 내용을 버전·`mode`(test/live)·고유 nonce·`merchantId`·서비스·주문번호·금액·통화·승인/만료시각과 묶어서 **서버 보유 발급기 비밀키의 HMAC-SHA256**으로 검증합니다. 브라우저 JSON에 `approved:true`가 있거나 `source:'trusted_order_issuer'`가 들어 있는 것만으로는 사업자 MID를 선택할 수 없습니다.
- `selectServerApprovedMerchant`는 해당 프로세스 안에서 검증된 **불변 주문 객체**만 수락합니다. 테스트 서명으로 운영 MID를 선택하거나, 인증 객체를 복사·수정해 재사용하면 차단합니다. 실제 사용자는 서명이나 비밀키를 제출하지 않고, 주문 발급 주체의 서버와 EKODI Pay 백엔드가 직접 검증합니다.
- `ekodipay_issuer_nonce_claims`는 `(merchant_id, issuer_ref, pg_mode, nonce)`와 `order_id`의 **원자적 유일성**을 저장하도록 설계한 보호된 D1 스키마입니다. 발급 서명 검증, 신뢰 원장 내 주문 상태 조회, 그 결과의 nonce claim INSERT가 완료되기 전에는 PG 확정 요청을 시작할 수 없습니다. 단순 메모리 캐시나 서명 검증만으로 재사용을 막았다고 주장하지 않습니다.
- `ekodipay-bank-account-fingerprint.js`는 PG 계약의 정산계좌번호를 **서버 메모리 안에서만** 입력받아 독립 HMAC-SHA256 비밀키로 `bankCode + 계좌번호` 지문을 계산합니다. 전체 계좌번호는 반환·DB 저장·감사로그 출력하지 않고, 은행코드·끝 4자리·지문만 전달합니다. 키 분실·회전 시 기존 지문과 새 지문을 무턱대고 혼합하지 말고 별도의 승인된 전환 및 대조 절차를 사용해야 합니다.
- `ekodipay_bank_credit_proofs`는 **인증된 은행 입금 거래 참조·사업자별 계좌 HMAC·원화 입금액·검증자·증빙 참조**를 별도 보존할 스키마입니다. 해당 사업자의 정산대사 배치가 완전한 PG 데이터로 대조되고, 정산계좌 명의 검증 상태와 지문이 일치하지 않으면 저장을 거부합니다. 동일 사업자 입금 증빙 중복 삽입과 사후 금액 변경을 금지합니다. 단, 이 스키마만으로 은행 입금의 진위가 자동 확인되는 것은 아니며, **독립된 금융기관·은행 명세 검증**이 필요합니다.
- **아직 실제 PG 코어에 연결되지 않았습니다.** 이 DB 마이그레이션은 참고용이며 운영 DB에 적용하지 않았습니다. 승인·취소·재시도 정책, 테넌트별 원장과 DO 잠금, 독립 시크릿 저장소 및 실제 발급 주체 인증을 별도로 통합한 후 검증해야 합니다. 무엇보다 테스트·운영 키를 섞거나 실제 카드 청구를 허용하지 않습니다.

**아직 미구현**: 사업자 생성/승인 관리자 API 및 UI, 인증된 주문 발급기 실연결, 기존 단일 사업자 결제 코어 #4877과의 어댑터, 독립 비밀 관리자 및 PG API 페이지네이션 배치, 웹훅·환불/정산 원장 운영 적용, 은행 자동 입금 증명 연계. 이 범위는 실제 PG 계약과 승인 자료 확인 후 후속 보호된 PR로 진행합니다.

## 5. 보호된 연계 전 필수 기술 조건 (2026-10 강화)

- **승인 주문 발급기**: `merchantId`와 `issuerRef`는 브라우저 입력값이 아닌 인증된 서버/전용 원장에서 조회합니다. 발급 증명 참조(`issuerProofRef`), 승인 시각(`approvedAt`), 만료 시각(`expiresAt`)을 포함하고, 승인 후 24시간 이내/미만료·금액 100원 이상·토스의 64자 이내 주문번호만 사용합니다. 단순 `source: trusted_order_issuer` 문자열은 인증 증거가 **아닙니다**. 서명된 서버-서버 증명 또는 신뢰된 DB 원장의 승인 상태를 검증해야 하며, 본 모듈만으로 그 경계가 성립하지는 않습니다.
- **환경과 키**: `test` / `live`를 호출 시 명시하지 않으면 오류를 반환하며 자동으로 테스트 모드를 선택하지 않습니다. 키 형식 검사는 PG 계약·MID 소유권을 대체할 수 없습니다. 운영키는 계약 MID와 토스 관리자에서 독립적으로 대조합니다. 앱의 기본 금전 거래 차단 설정은 그대로 유지합니다.
- **정산 증빙**: 토스 `GET /v1/settlements`는 페이지 단위이며 최대 `size=5000`과 응답 60초를 고려해야 합니다. 실제 호출하는 별도 작업자는 서버에서 자기 사업자의 시크릿 키만 사용하고, 429 재시도/전체 페이지 완료 확인 이후 대사해야 합니다. 빈 정산 자료가 ‘입금 확인 0원’인 것처럼 확정되면 안 됩니다. 인증된 은행 거래명세의 **입금 방향**과 개별 거래 참조값, 계좌 HMAC 지문, 금액이 일치할 때만 `bank_verified`를 허용합니다.
- **DB 연결 제약**: 사업자 간 계좌 HMAC 중복을 불허하고, 정산기록은 승인 주문의 사업자·환경·MID가 모두 일치해야 합니다. 무결성 실패/중복/타 사업자 조회는 전송 중단 및 감사 대기합니다. 스키마는 현재 참고용이며 프로덕션 D1에는 적용하지 않았습니다.
- **기존 단일 MID 결제 코드와 연결**: #4877이 사용하는 단일 `ekodibiz` 전역 키를 다중 사업자용 기본값으로 사용하면 안 됩니다. 해당 코어의 상점 선택·Durable Object 파티셔닝·PG 승인 확인·콜백·재대조를 사업자마다 독립시키는 별도 리뷰/운영 실증이 끝날 때까지 다중 MID 실거래를 금지합니다.

## 6. 실제 연결 전 사업자별 요청자료

비밀키·계좌번호를 채팅에 보내지 말고 PG 관리자/안전한 비밀 저장소에서 입력합니다.

- 법적 판매자명, 사업자 등록·심사 진행 여부, 담당 책임자.
- PG사명, 계약 계정, 승인된 MID 목록과 결제수단(일반/간편/계좌 등), 테스트/라이브 키 발급 상태 **(키값 제외)**.
- 정산 금융기관, 계좌 명의 일치·등록 확인 여부, 정산 주기와 PG 수수료율 **(전체 계좌번호 제외)**.
- 각 서비스별 주문 발급 담당 백엔드, 계약/견적 승인 상태, 이중 승인 담당자.
- 이용약관/고객센터/환불 정책, 세금계산서·현금영수증 처리 책임.
