# EKODIBIZ 기관형 AI: 연속성·보안 우선 실행 계약

Issue: [#9870](https://github.com/topmaster-joseph/ekodi-platform/issues/9870)  
Owner: EKODI Orchestrator · EKODIBIZ (기존 AI 구매·결제 위탁계약과 별도 서비스)

## 1. 목표와 현재 경계

기관이 사용하는 AI 모델·공급사가 바뀌어도 **업무 상태·승인·기록은 에코디 기관 경계에 남도록** 한다. 외부 AI 또는 결제 서비스 오류가 무단 재시도나 교차기관 데이터 유출로 이어지지 않아야 한다.

- 이번 단계: **서버 대 서버 전용 보안 API + 기관별 전용 Durable Object SQLite에 암호화 기록과 대화 맥락 + 멱등 처리 + 감사 체인 + 승인 체크포인트 + 단건 표준 내보내기**.
- 이번 단계에서는 **AI 모델 자동 호출, 외부 메일/결제/전자결재, 사용자 직접 로그인, 공급사 구독 변경, 실결제 활성화가 모두 없음**.
- **환경 보호 게이트**: 모든 민감한 기관형 AI API는 `EKODIBIZ_MODE=isolated-staging`이고 `INSTITUTION_AI_STAGING_PILOT_ENABLED=true`인 경우에만 열리며, 나머지 환경에서는 비밀키가 존재하더라도 HTTP 503으로 차단한다. 현재 운영 환경 `operational-mvp`에서 기관형 AI를 활성화할 수 없도록 설계했다. 스테이징에 테스트 비밀키를 별도로 설정하더라도 실제 기관 개인정보는 사용하지 않는다. 실운영 개통은 별도 보호된 보안·릴리스 검증 이후에만 구현한다. 문서의 목표를 현재 실운영 보장이라고 표현하지 않는다.
- 별도 구성된 서버 측 애플리케이션만 비밀 키를 사용한다. 브라우저, 모바일 앱, QR 링크, 학생/직원 프런트엔드에 키 제공 금지.
- 기존 /ekodibiz/ai-agency 계약·결제 워크플로 및 안전 플래그는 변경하지 않는다.

## 2. 독립성과 테넌트 보안

정본 데이터 소유자는 **고객 기관**이며 AI 모델 응답 ID 또는 공급사 기록을 정본으로 삼지 않는다.

- 입력: POST /api/institution-ai/v1/submit (tenantId, operationId, taskType, classification, payload)
- 대화 누적: POST /api/institution-ai/v1/message (기관 서버가 검증한 user/assistant 메시지, 메시지별 고유 ID와 기대 버전 필수, 최대 200회·메시지당 4,000자)
- 조회: POST /api/institution-ai/v1/status
- 승인: POST /api/institution-ai/v1/approve
- 처리 상태: POST /api/institution-ai/v1/checkpoint
- 내보내기: POST /api/institution-ai/v1/export
- 상태: GET /api/institution-ai/v1/health (비밀·기관 목록·개인정보 미노출)

**요청별 인증**: 요청 본문 tenantId와 서버가 보유한 해당 기관·역할 키를 직접 비교한다. 사용자 메시지 제출, AI 응답 작성, 조회/내보내기, 승인, 실행 체크포인트의 키는 분리한다. 특히 제출 역할의 키로 AI 응답을 위조할 수 없고 AI 응답 역할의 키로 사용자 메시지를 위조할 수 없게 서버에서 검증한다. 조직 A의 키로 B의 데이터를 조회하거나 수정하는 요청은 거절한다. 기관별 서비스 사용 전 인증 서버에서 역할·고용 상태·승인자를 검증할 책임이 있다. 역할 키만으로 개인 신원확인을 보장한다고 주장하지 않는다.

**저장 암호화**: payload만 AES-256-GCM으로 암호화하고, tenantId + operationId + keyVersion을 암호화 추가 인증 데이터(AAD)에 묶는다. HKDF 기반 기관별 파생 키를 사용한다. 암호화 마스터는 버전별 키링으로 교체할 수 있으며 과거 키는 복구·내보내기가 완료되기 전까지 폐기하지 않는다. 나머지 작업 ID·종류·분류·처리상태·일시는 운영 메타데이터로 저장된다.

**감사 무결성 강화**: 각 변경 이벤트에는 당시 암호문·메시지·권한 분류·작업 상태·버전 등 작업 정본의 SHA-256 스냅샷 지문을 연결한다. 조회 및 내보내기 전 이벤트 체인과 최종 스냅샷 지문을 모두 검증하고, 누락·불일치 시 503으로 차단한다. 기존 지문이 없는 기록은 자동으로 신뢰하거나 덮어쓰지 않으며 복구·마이그레이션 검토 대상으로 분리한다.

**중요 한계**: 현재는 기존 RevenueStore 클래스를 재사용하되 각 기관별 고유 Durable Object 인스턴스를 사용하고 키 접두어도 기관별로 격리한다. 대규모 기관, 규제 자료 또는 엄격한 계약상 물리적 분리 요구에는 별도 인프라·KMS·백업 및 접근감사를 별도 제공해야 한다. 관리자·스토리지 권한이 침해된 경우 감사 해시 체인만으로 법적 불변성을 증명할 수 없다. 외부 불변 저장소에 정기 증빙·복구 검증이 필요하다.

## 3. 필수 Worker secrets (예시 구조, 실제 비밀 금지)

- `INSTITUTION_AI_TENANTS_JSON`: 기관 ID별 `{ "status": "active", "keys": { "submit": ["..."], "assistant": ["..."], "read": ["..."], "approve": ["..."], "execute": ["..."] } }` JSON. 키는 각각 32바이트 이상 고강도 난수; 이전 키+신규 키를 최대 3개까지 일시 병행 후 폐기한다
- `INSTITUTION_AI_KEYRING_JSON`: `{ "v1": "<32바이트 이상 마스터>", "v2": "<교체용 마스터>" }` JSON
- `INSTITUTION_AI_ACTIVE_KEY_VERSION`: 위 키링의 활성 버전
- `INSTITUTION_AI_HMAC_KEY`: 별도 32바이트 이상 키; 암호화 키 회전과 무관하게 멱등 생성 지문 유지
- `REVENUE_STORE`: 기존 Worker의 SQLite Durable Object 바인딩

secret 바인딩이 없거나 잘못되면 요청은 503으로 닫히며 접수된 것으로 표시하지 않는다. 비밀정보를 GitHub, 로그, 프런트엔드, URL, 데모 QR에 기록하지 않는다.

## 4. 업무 연속성 상태 전이

- 읽기·초안 계열: `queued → processing → completed` (완료 시 증거 참조 필수). 오류 시 `blocked` 또는 `needs_reconciliation`으로 보류
- 외부 영향 큰 업무: `awaiting_approval → approved → processing → needs_reconciliation` (검증된 외부 실행 어댑터가 없으므로 완료 상태로 전환 불가)
- 모든 상태 변경은 이전 `expectedVersion` 검증과 별도 역할 키가 필요하며 감사 레코드에 SHA-256 연결 해시를 남긴다
- 잘못된 재시도는 `IDEMPOTENCY_CONFLICT`; 모호한 쓰기 결과는 무조건 `needs_reconciliation`에 잠그고 외부 거래를 맹목적으로 재실행하지 않는다
- 전환된 AI 공급사는 이전 작업 ID, 기관 정본 자료, 승인기록을 소유하지 못한다

AI 호출은 후속 단계에서 중앙 `ai-resilience-runtime.js` 및 `ekodi-ai-provider-registry.js`와 연결하되, 기관별 허용 모델 목록과 민감도 정책을 **AI 요청 본문 전송 전에** 검사해야 한다. 기밀·제한 자료의 외부 전송은 기본 금지이며, 별도 계약·분류·승인과 개인정보 영향평가 뒤에만 허용한다. 공급사 장애 시 안전한 작업 큐·수동 모드로 전환하며 '완료'로 위장하지 않는다.

## 5. 복구, 실증 및 단계별 가드

**스테이징 복구용 아카이브 API (추가 구현)**:
- `POST /api/institution-ai/v1/backup`: 작업·암호화된 메시지·감사 체인을 **독립된 백업 키**로 한 번 더 AES-256-GCM 암호화하여 반환. 기관별 `backup` 역할 서버 키만 호출 가능. 개인정보·작업 평문과 복호화 키는 아카이브에 넣지 않는다.
- `POST /api/institution-ai/v1/restore-check`: 별도 `restore` 권한으로 아카이브 복호화, 기관/작업 ID 일치, 감사 무결성 및 실제 작업 데이터 복호화 가능성을 **읽기 전용** 검증한다.
- `POST /api/institution-ai/v1/restore`: 앞의 검증 후 **기존 기록이 없는 기관별 저장소에서만** 작업+감사기록을 원자적으로 복원. `INSTITUTION_AI_RESTORE_ENABLED=true`를 추가로 요구하며 기존 기록은 덮어쓰지 않는다. 재실행·외부 결제·발송·게시 동작은 하지 않는다.
- 백업 키 설정: 별도의 Worker secrets `INSTITUTION_AI_BACKUP_KEYS_JSON` (예: `{"v1":"<32byte secret>"}`), `INSTITUTION_AI_BACKUP_KEY_VERSION=v1`. 과거 아카이브가 남아 있으면 과거 키를 보존하고 격리해 관리한다.
- **시범 구현 한계**: 이 아카이브는 최대 12KiB의 단건 기록만 지원하며 더 큰 기록은 **413**으로 거절한다. 자동 오프사이트 저장, 주기적 스냅샷, 다건/대화 대용량 청크 백업, 독립 불변 저장소, KMS, 복구계획(RPO/RTO), 기관별 보존·삭제 정책, 운영환경 복원은 **아직 구현·검증되지 않았다**. 예시 키·실제 기관 자료로 테스트하지 않는다.

**현재 구현된 단건 대화 포함 내보내기**는 공급사와 독립적인 `ekodi.institution-ai.work/v1` 형식으로 작업·이벤트·자료를 반환한다. 전체 기관 일괄 내보내기, 정기 백업, 별도 지역 재해복구, 실제 복원 검증은 후속 운영 조건이다.

제한적 시범 운영 전에 반드시 아래 검증을 마친다.

1. 중앙 인증·SSO 또는 기관 서버 위임자별 검증, 승인자 고유식별 증명, 키 분실/회수 시나리오
2. 여러 기관 계정으로 교차기관 읽기/쓰기/내보내기 침투 테스트
3. 암호화 키 손실·오염, 키 회전·복구, 백업 정본/불변 감사증빙 확인
4. AI 장애·모델 교체·사용량 초과·공급사 계약 중단, 무대응/중복 쓰기/모호한 결과 시험
5. 개인정보·공공기관 보안·국외 이전 및 위수탁 책임 검토, 보존기간·삭제/반출 프로세스
6. 장애 복구 훈련으로 실제 RPO/RTO를 산출하고 기관별 SLA 명시
7. 보호된 CI → 격리 스테이징 → 거부/성공 카나리 → 오케스트레이터 릴리스 → 실서비스 확인

**생성형 AI 사용 연속성은 백업과 인증이 먼저다.** 표준 내보내기 API가 동작한다고 백업·복구가 완성되었다고 주장하지 않는다.

## 6. 테스트

`node --test test/ekodibiz-institution-ai.test.mjs`

테스트 항목: 구성 누락 차단, 키/역할/테넌트 분리, 브라우저 차단, 암호문 저장, 멱등 요청과 충돌 거절, 키 회전 뒤 복호화, 증거 없는 완료 거절, 외부 행위 승인/재시도 차단, 감사 무결성 검증, 큰 입력 제한, 민감도별 외부 모델 전송 금지.

**판정**: 기능 테스트와 배포만으로 기관 보안·연속성을 '반드시 확보했다'고 단정하지 않는다. 위 단계별 검증 증거를 갖춰야 기관 운영 SLA를 약속할 수 있다.
