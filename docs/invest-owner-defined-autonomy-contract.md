# 마이투자 — 사용자 지정 한도 안에서 AI 자율운용 (최상위 제품 계약)

## 목적과 화면
마이투자의 목적은 본인 명의 증권계좌를 연결하고, AI가 실제 잔고·보유자산·검증된 시세를 분석한 뒤, **소유자가 한 번 승인한 운용 범위 안에서 건별 추가 승인 없이** 지속적으로 투자하도록 하는 것이다. 이는 수동 주문 도우미나 다수의 연구실을 늘리는 사업이 아니다.

기본 화면은 **① 내 증권계좌 ② AI 분석 ③ 내 한도 안에서 자동운용** 세 기능과 저장된 주요 한도를 우선 표시한다. 심화 연구/보고 기능과 위험관리 내부 구현은 유지하되, 첫 화면에서 모두 펼치지 않는다. 새 증권사 계좌를 연결할 때까지 가상 잔고를 실계좌처럼 표시하지 않는다.

## 사용자가 선택하고 승인할 것
소유자가 직접 지정: 운용 총자금, 1회 주문금액 상한, 1일 매수 상한, 일·누적 손실 제한, 최소 현금 비중, 개별 종목 비중과 보유종목 수, 거래시장·자산 유형·허용시간·일일 횟수. 정책의 필수항목은 기본적으로 미설정이다. 예시 프리셋은 별도의 명시적 저장 전에는 적용하지 않는다.

위험 허용 범위 확대(자금·주문·손실·거래 빈도·운용기간 증대, 현금보유 축소, 거래시간 연장, 시장·자산 범위 확대, 알림 축소)는 기존 실거래 승인을 무효화한다. 신규 본인 확인과 최신 정책 지문에 묶인 재승인이 필요하다. 범위를 좁히는 것은 재승인 없이 가능하며 긴급정지/일시정지는 항상 가능해야 한다.

## 범위 내 자율 운영 — 의도한 최종 상태
1. 공식 증권사 연결: 소유자 검증, 서버 금고에 비밀정보 저장, 계좌/잔고/주문·체결 내역 조회, 실제 계좌와 가상 데이터 구분.
2. AI 판단: 정합성 확인된 시장가격·재무 및 계좌/보유 현황을 읽어 전략 신호와 매수·보유·매도 근거 생성. 불충분한 데이터에는 거래 신호 생성 금지.
3. 독립 위험 엔진: 위 소유자 설정 정책 + 주문의 최신성/중복/시세 이탈/가용현금/포지션/거래정지/실현 및 평가 손실/장부대사/브로커 상태를 **매 주문마다** 검사. AI가 이 검사를 우회할 수 없어야 한다.
4. 브로커 주문·확인: 검사를 통과한 지정가 주문을 허용된 계좌에서만 실행. 주문 ID와 체결/미체결/부분 체결을 조회해 재시도 중복 주문을 막고 장부를 맞춘다.
5. 사후 통제: 사용자에게 매매 근거·잔고 변화·손익·위반 알림 제공. 긴급정지·계좌 장애·시세 불확실성·정책 지문 불일치 시 **새 주문 중지**. 긴급정지가 손실을 한도에서 보장하거나 시장의 기존 포지션을 자동 청산한다는 뜻은 아니다.

최종 운용 모드는 소유자가 활성화하는 `자동운용 켜기/일시정지/긴급정지`이다. 매 주문마다 추가 승인을 요구하지 않되 모든 주문은 소유자의 **기존 승인 정책** 및 독립 위험 엔진의 허가가 필요하다.

## 현재 구현 상태 / 건너뛰면 안 되는 단계
- `invest-broker-readonly-adapter.js`: 한국투자증권 KIS 조회 전용 어댑터. 운영 토글+서버 비밀정보+강한 본인인증 없이는 실제 잔고로 판단하지 않는다.
- `invest-autopilot-core.js`: 소유자 정책 유효성·승인 범위 변경 판단·모의 주문 위험관리.
- `invest-autopilot-runtime.js`: 연구/모의운용만 가능. AI 분석을 **실제 잔고·최신 시세**에 연결하고, 증권사 실거래 주문·체결 조회를 검증한 완성 경로는 아직 없다.
- `INVEST_MARKET_POLICY.autonomousLiveTrading=false` 및 운영 실주문 잠금은 유지. 이 문서와 화면 개편, 모의운용 승인, 과거의 일반 개발 승인은 **실자금 주문의 실행 허가가 아니다**.
- 실거래 활성화 전에 소유자 본인 실계좌 검증, KIS 이용조건·정식 주문 API 확인, 인증·중복주문·체결동기화·복구 검증, 최소 60일 검증된 모의운용, 수수료·시장데이터 조건 검토, 별도 명시적 실거래 활성화와 거버넌스 배포를 통과해야 한다.

## 운영·배포
정식 진입은 `https://ekodi.kr/invest/my`. 보호된 소스 PR → 헌법·CI·보안·중복가드 → 공식 오케스트레이터 복구·병합 → 스테이징 → 운영 배포 → 실서비스 인증/화면/응답 검증 → 단계별 완료 보고. 계좌번호·API 비밀키·OTP는 이슈/로그/AI 입력으로 받지 않는다.

**기본 원칙: 사용자의 한도 아래 자율성은 높이고, 사용자의 한도를 넘는 권한은 없게 한다.**
